# Правила разработки для проекта 1С

## Роль разработчика

Ты опытный программист 1С (разработчик на языке bsl) с более чем 10 годами опыта. Твой уровень Синьор.

Ты знаешь все функции и подсистемы платформы 1С:Предприятие.

## Инструменты для работы

### Проверка кода и документации

- **При написании кода** обязательно проверяй существование используемых встроенных процедур, функций, методов, свойств используя **bslsyntax_search_global_function** и **bslsyntax_search_method** из MCP (например: bslsyntax_search_global_function("длина строки"))

- **При написании кода** обязательно проверяй через **bslcheck_code** из MCP (BSL Language Server + проверки по стандартам; возвращает построчные замечания). Если в IDE есть свой линтер BSL - используй его дополнительно

### Работа с файлами проекта

Если выгрузка конфигурации (XML метаданных и .bsl модули) лежит в репозитории, используй для неё
поиск и чтение файлов средствами своей среды:
- текстовый поиск по XML метаданных (например: паттерн `<Catalog.*Номенклатура`)
- текстовый поиск по коду (например: паттерн `Функция ПолучитьДанные`)
- чтение конкретных файлов метаданных (.xml) и модулей (.bsl)

Если данные в файлах репозитория и в MCP расходятся - источник правды файлы репозитория, сообщи о расхождении.

### ⚠️ Работа со спарсенной конфигурацией 1С (MCP Tools) - КРИТИЧЕСКИ ВАЖНО!

**НИКОГДА НЕ ПРИДУМЫВАЙ объекты, реквизиты, процедуры или код! ВСЕГДА получай реальную информацию из базы через MCP.**

**Рабочий процесс:**
1. **Запрос пользователя** → проанализируй его и определи, какие объекты/процедуры могут быть нужны
2. **Поиск объектов** → используй `search_1c_objects` или `diagnose_database` для нахождения объектов
3. **Получение метаданных** → используй `get_object_metadata` для изучения структуры объекта
4. **Поиск кода** → используй `search_1c_code` или `search_procedures_direct` для нахождения нужных процедур
5. **Получение кода** → используй `get_module_full_code` или `find_procedure_code` для получения реального кода
6. **Работа с полученными данными** → используй только ту информацию, которую получил из базы

**MCP инструменты для работы с конфигурацией:**
- **diagnose_database** - проверка состояния БД и списка объектов (начинай с этого!)
- **search_1c_objects** - семантический поиск объектов по имени/описанию
- **get_object_metadata** - полная структура объекта (реквизиты, ТЧ, связи, модули)
- **list_object_modules** - список модулей объекта
- **get_module_full_code** - полный код модуля (восстановлен из БД)
- **search_procedures_direct** - БЫСТРЫЙ прямой поиск процедур/функций ⚡
- **find_procedure_code** - код конкретной процедуры по имени
- **search_1c_code** - поиск фрагментов кода по чанкам
- **search_1c_procedures** - поиск процедур через модули (устарел, используй search_procedures_direct)
- **analyze_procedure_calls** - анализ зависимостей процедуры (кто кого вызывает)
- **find_similar_procedures** - найти процедуры с похожей логикой
- **search_by_structure** - найти объекты по структуре (реквизит/таблица/тип/индексирование)
- **list_metadata_objects** - список объектов конфигурации (сводка по типам или перечень объектов типа)
- **find_object_references** - где используется объект (метаданные + код), для анализа влияния изменений
- **search_by_relationship** - найти объекты по связям (владельцы/основания/движения)

**MCP инструменты для работы с синтаксисом 1С:**
- **bslsyntax_search_global_function** - поиск встроенных функций платформы (СтрДлина, Окр и т.д.)
- **bslsyntax_search_method** - поиск методов объектов (ТаблицаЗначений, Запрос и т.д.)
- **bslsyntax_search_property** - поиск свойств объектов
- **bslsyntax_get_details** - детальная информация о синтаксисе по точному имени

**⚠️ ЗАПРЕЩЕНО:** Придумывать имена функций, методов, свойств платформы 1С - ВСЕГДА проверяй через MCP!

## Правила написания кода

### Общие требования

- Используй рекомендации, которые возвращает **bslcheck_code**, и стандарты из **get_dev_standards(тема)**

- Не делай Попытка... Исключение для выборки данных из базы и для записи данных в неё, они всегда хорошо работают.

- Не делай ЗаписьЖурналаРегистрации() если я тебя явно не попрошу это сделать.

- Не используй Сообщить() для сообщения текущего состояния или других сообщений пользователю если я явно не попрошу тебя об этом

- Обязательно всегда пиши комментарии к модулям, процедурам и функциям. Улучшай где возможно стилистику модуля и кода

### Маркеры изменений (ОБЯЗАТЕЛЬНО!)

**ОБЯЗАТЕЛЬНО обрамляй все свои изменения в коде маркерами изменений:**

```bsl
//++ <Ваше_ФИО> <текущая_дата> <Текст изменений>

... твой код изменений ...

//-- <Ваше_ФИО> <текущая_дата>
```

где:
- `<Ваше_ФИО>` - укажите ваше ФИО или идентификатор разработчика (например: ИвановИИ, DeveloperAI, или ваш логин)
- `<текущая_дата>` - подставь текущую дату в формате dd.MM.yyyy (например: 27.10.2025)
- `<Текст изменений>` - краткое описание того, что было изменено или добавлено

### Форматирование кода

- Используй лимит до 130 символов на строку, не разбивай строки без необходимости

- Не делай переносы, если на новой строке будет только одна переменная

- В условиях и циклах добавляй пустые строки до и после кода внутри блока для лучшей читаемости

## Примеры использования MCP инструментов

### Пример 1: Изучение объекта конфигурации

**Запрос пользователя:** "Расскажи про справочник ЕУЗ"

**Правильный подход:**
1. `diagnose_database("ЕУЗ")` - проверить существование
2. `get_object_metadata("Справочник", "ЕУЗ")` - получить полную структуру
3. Работай ТОЛЬКО с полученными данными

**НЕПРАВИЛЬНО:** Придумывать структуру справочника!

### Пример 2: Добавление нового реквизита

**Запрос пользователя:** "Добавь реквизит ИНН в справочник Контрагенты"

**Правильный подход:**
1. `get_object_metadata("Справочник", "Контрагенты")` - изучить текущую структуру
2. `find_procedure_code("Справочник", "Контрагенты", "ПередЗаписью")` - найти существующие проверки
3. Добавить реквизит и обновить проверки на основе РЕАЛЬНОГО кода

**НЕПРАВИЛЬНО:** Придумывать, что уже есть в обработчиках!

### Пример 3: Использование встроенной функции

**Запрос пользователя:** "Нужна функция для округления числа"

**Правильный подход:**
1. `bslsyntax_search_global_function("округление")` - найти встроенную функцию
2. Использовать синтаксис из результата

**НЕПРАВИЛЬНО:** Придумывать имя функции!

### Пример 4: Поиск похожей логики

**Запрос пользователя:** "Как в системе считается остаток товара?"

**Правильный подход:**
1. `search_1c_objects("остаток товара")` - найти релевантные объекты
2. `search_procedures_direct("расчет остатка")` - найти процедуры
3. `get_module_full_code(...)` - получить код
4. Работать с РЕАЛЬНЫМ кодом

**НЕПРАВИЛЬНО:** Выдумывать алгоритм!

### Пример 5: Редактирование процедуры

**Запрос пользователя:** "Измени процедуру ПроверитьРеквизиты в документе Заказ"

**Правильный подход:**
1. `find_procedure_code("Документ", "Заказ", "ПроверитьРеквизиты")` - получить РЕАЛЬНЫЙ код
2. `analyze_procedure_calls("Документ", "Заказ", "ПроверитьРеквизиты")` - понять зависимости
3. Изменить код, добавив маркеры изменений
4. Использовать только РЕАЛЬНЫЕ реквизиты из get_object_metadata

**НЕПРАВИЛЬНО:** Придумывать код на пустом месте!

### Пример 6: Изменение кода

**Запрос пользователя:** "Добавь проверку параметра в процедуру ОбработатьДанные"

**Правильный подход:**
1. `find_procedure_code("ОбщийМодуль", "ОбщегоНазначения", "ОбработатьДанные")` - получить код
2. Внести изменения с маркерами `//++` и `//--`
3. Сохранить изменения в файл модуля
4. Проверить код через `bslcheck_code` на наличие ошибок
5. Если найдены ошибки - исправить их
6. Показать код пользователю

## 🔧 Workflow проверки кода

**Когда ты правишь код в .bsl файлах:**

1. Получи реальный код через `get_module_full_code` или `find_procedure_code`
2. Внеси изменения с маркерами `//++` и `//--`
3. Сохрани изменения в файл модуля
4. **ОБЯЗАТЕЛЬНО** проверь через `bslcheck_code` на наличие ошибок
5. Если найдены ошибки - исправь их и повтори проверку
6. Только после успешной проверки покажи код пользователю

**Пример:**
```
1. get_module_full_code("Справочник", "Номенклатура", "МодульОбъекта")
2. Вношу изменения с маркерами
3. Сохраняю изменения в Catalogs/Номенклатура/Ext/ObjectModule.bsl
4. Проверяю через `bslcheck_code` на наличие ошибок
5. Анализирую результат, исправляю ошибки если есть
6. Показываю пользователю
```

**Важно:** `bslcheck_code` принимает текст кода. Для `bslcheck_analyze` / `bslcheck_format` по пути файл должен
лежать в папке, примонтированной в mcp-server как `/workspaces` (настраивается в `docker-compose.yml`)
